## Enhancement 1: Prove the Wiring

### Useful GSD idea

GSD verifies backward from the outcome:

```text
observable truth -> necessary artifact -> critical wiring -> behavioral proof
```

It distinguishes missing, stubbed, orphaned, and wired artifacts. It also
refuses to treat symbol presence or wiring alone as proof for state transitions,
cancellation, cleanup, or ordering behavior.
([`verify-phase.md:1-18`](https://github.com/open-gsd/gsd-core/blob/6ee43492723dababa4138ceb72fd2cd26d4325d9/gsd-core/workflows/verify-phase.md#L1-L18);
[`verify-phase.md:111-180`](https://github.com/open-gsd/gsd-core/blob/6ee43492723dababa4138ceb72fd2cd26d4325d9/gsd-core/workflows/verify-phase.md#L111-L180))

### What Matt's composition already supplies

Matt's vocabulary supplies tracer-bullet vertical slices, proof seams, fixed
points, and separate Spec/Standards review. Those concepts already favor
observable behavior over horizontal file work. The missing pressure is the
explicit question: **is the artifact connected to the path that delivers the
promised behavior?**
([`matt-pocock-skills-vocabulary.md:105-177`](../../language/skill pack ideas/matt-pocock-skills-vocabulary.md#L105))

### Smallest useful local enhancement

The engineering contract is the primary owner because wiring is shared proof
discipline, not a new workflow. `$to-tickets` should plan critical connections;
`$implement` and `$review` should enforce only the local slice they need.

The enhancement should recruit this behavior:

- start from observable acceptance;
- identify the necessary artifacts and critical connections;
- prove the real path reaches and uses them; and
- require behavioral evidence when presence and connectivity cannot establish
  meaning.

Local **semantic proof**, **proof seam**, and **proof lane** remain the stronger
vocabulary. Do not introduce `goal-backward verification` as a second proof
system.
([`engineering-contract.md:15-24`](../../../agents/engineering-contract.md#L15);
[`engineering-contract.md:38-71`](../../../agents/engineering-contract.md#L38);

## Enhancement 2: Preserve Must-Not Commitments

### Useful GSD idea

GSD models positive truths and prohibitions separately. A prohibition means the
delivered result is wrong if the forbidden behavior occurs; it is not merely
work omitted from scope. Mechanically enforceable prohibitions fail closed when
their required check is absent or cannot demonstrate a controlled violation.
([`verify-phase.md:54-83`](https://github.com/open-gsd/gsd-core/blob/6ee43492723dababa4138ceb72fd2cd26d4325d9/gsd-core/workflows/verify-phase.md#L54-L83))

### Distinction that matters

- **Non-goal / exclusion:** this work does not promise to build the behavior.
- **Must-not commitment:** the delivered system must prevent the behavior.

The second changes acceptance and proof. Examples include “must not log the
secret,” “must not bypass authorization,” and “must not mutate tracker state in
read-only mode.”

### Smallest useful local enhancement

`$to-spec` should own the distinction because it already owns requirements,
exclusions, invariants, acceptance, and proof authority. A must-not commitment
should remain source-traced and receive observable acceptance plus proof
proportionate to its meaning. `$to-tickets` should carry it only when it affects
a child slice; implementation and review should consume it as Spec.

The engineering contract's existing **negative control** remains the proof
owner for validators, hooks, dependency boundaries, and enforcement rules. Do
not generalize every non-goal into a negative test.
([`to-spec/SKILL.md:53-70`](../../../../skills/custom/to-spec/SKILL.md#L53);
[`to-tickets/SKILL.md:53-72`](../../../../skills/custom/to-tickets/SKILL.md#L53);
[`engineering-contract.md:57-71`](../../../agents/engineering-contract.md#L57))

### Required behavioral test before adoption

Use a source packet containing both:

- a genuine exclusion, such as “export UI is out of scope”; and
- a must-not commitment, such as “the endpoint must not return private fields.”

The successful candidate must keep the exclusion out of implementation while
preserving the prohibition as an acceptance and proof obligation. Reject
wording that turns every exclusion into work, silently drops the prohibition,
or invents a mechanical check when only human judgment can establish it.

## Do Not Prioritize

| GSD Idea | Disposition |
| --- | --- |
| One-way-door ratings and checkpoints | The concrete undo-cost explanation is good wording pressure, but local commitment, migration, rollback, irreversible-state, and user-decision rules already own the behavior. Test only if a real failure appears. |
| Discuss -> Plan -> Execute -> Verify -> Ship | Reject. It replaces skill composition with mandatory phases. |
| `.planning/STATE.md` and lifecycle hooks | Reject. `$handoff`, `/compact`, tracker state, and repo owners already cover continuity without a second project-state spine. |
| Separate `fast` and `quick` skills | Reject. Tiny work already compresses to `Explore -> Prove -> Lock`; extra entry points increase cognitive load. |
| Namespace routers and smart-next commands | Reject. `$skill-router` already returns exactly one next route and stops. |
| Persistent debug sessions | Reject. `$diagnosing-bugs` owns diagnosis and `$handoff` owns cross-session context. |
| Fixed task counts or context percentages | Reject. Semantic scope, proof, dependencies, and independence are stronger bounds. |
| Per-task commits, phase summaries, plan checker, and deviation ledger | Reject. They fragment `$implement`'s one-item, one-Lock, one-commit boundary. |

GSD itself acknowledges the relevant costs: its phase loop adds overhead,
latency, and ceremony, and it recommends skipping the loop for work that fits
one short prompt and one agent turn.
([`context-engineering.md:100-124`](https://github.com/open-gsd/gsd-core/blob/6ee43492723dababa4138ceb72fd2cd26d4325d9/docs/explanation/context-engineering.md#L100-L124))

## Recommended Extraction Order

1. Test the orphaned-artifact failure against current `$to-tickets`,
   `$implement`, and `$review` behavior.
2. If the failure is real, change the engineering contract as the single shared
   owner and add only required local slices.
3. Test exclusion-versus-prohibition handling against current `$to-spec`.
4. If the failure is real, change `$to-spec` first and propagate only the
   commitment needed downstream.
5. Stop if the current skills already handle either case. Do not add wording
   merely because GSD names the idea.

No new skill, router entry, persistent artifact, command, phase, flag, or
workflow step is justified by this source.
