### Blind findings and counterpressure

1. **Commitment ledger plus bidirectional trace.** NASA's requirement and
   verification guidance directly supports unique source identity,
   requirement-to-verification mapping, and traceability in both directions.
   The transferable method is to account for every source-owned commitment and
   every spec requirement without inventing lower-level work. This is
   `independently-supported` (B2, B3), with the inference that a compact
   commitment ledger is the lowest-burden local representation.

2. **Atomic, unambiguous, outcome-oriented requirements with explicit proof.**
   NASA supports one thought per requirement, consistent terminology,
   implementation-free statements, intelligible rationale/assumptions, and a
   named verification method (B2). GOV.UK independently supports outcome-based
   acceptance tied to the user need (B7). The method is
   `independently-supported`; literal “shall” syntax is not necessary and BCP
   14 capitals are applicable only when explicitly adopted (B4).

3. **Settledness is a gate, not document length.** NASA says assumptions should
   be confirmed before baselining and unresolved values need an owner,
   rationale, action, and date (B2). The supported local inference is that a
   detailed packet is not settled when a missing choice can change a
   commitment, acceptance condition, or boundary. Nonblocking notes may remain
   only when they cannot do so. Classification:
   `independently-supported` for confirmed assumptions/baselining;
   `unverified` for any universal “decision-complete” checklist.

4. **Proportionate completeness.** ISO 29148 owns the existence of required
   requirements-information content (B1), while ISO 25010 supplies a quality
   model useful for checking comprehensiveness (B9). NASA explicitly treats
   tailoring as expected (B6), NIST SSDF rejects checklist use in favor of
   risk/applicability (B10), and GOV.UK defers deeper story detail until work
   begins (B7). Thus “inspect every relevant concern, include only applicable
   obligations, and record deliberate non-applicability only when it prevents
   ambiguity” is `independently-supported`. A fixed exhaustive template that
   demands content in every section is counterindicated.

5. **Keep requirements and architecture description distinct.** NASA's
   “what, not how” test (B2) and ISO 42010's explicit separation between an
   entity, its architecture description, and entity requirements (B8) support
   recording already-settled interface/data/state constraints and pointers
   without choosing a new architecture. This is `independently-supported`.
   The alternative is a separately owned architecture/design decision when a
   new commitment is required.

6. **Risk- and context-derived cross-cutting obligations.** NIST SSDF supports
   tracking security requirements, risks, and design decisions with rigor
   selected by mission, risk, feasibility, and applicability (B10). NIST's
   Privacy Framework likewise derives desired privacy outcomes from data
   processing, roles, legal duties, stakeholder expectations, and risk
   tolerance (B11). Google SRE supports user-centered measurable operational
   objectives with explicit validity conditions (B12). This method is
   `independently-supported`; blindly inserting security, privacy, or
   operability boilerplate is not.

7. **State analysis only for material state distinctions.** NASA identifies
   state analysis as a requirements-analysis technique, but the accessible
   current appendix delegates its detail to a non-public expanded guide.
   Combining that thin direct support with risk-based tailoring yields a
   proportionate state-boundary matrix as a plausible inference, but the exact
   M0 branch vocabulary is `unverified` pending stronger direct evidence.

8. **Read-before-create and reconcile before retry.** RFC 9110 establishes
   that non-idempotent operations should not be automatically retried unless
   their semantics are known idempotent or the original is known unapplied
   (B13). Request IDs/idempotency keys are a supported alternative only where
   the transport provides them (B14, B15). When it does not, preserving the
   request/draft identity and reading the target state before any further
   mutation is `independently-supported`; blind retry is counterindicated.

9. **Boundary-preserving downstream handoff.** GOV.UK distinguishes
   outcome/acceptance material from deeper discussion when work starts (B7),
   while NASA traceability distinguishes higher-level need from justified
   lower-level decomposition (B3). The supported inference is that the parent
   spec should expose commitments, acceptance, dependencies, risks, and
   residual nonblocking gaps but leave implementation slicing to its owner.
   Classification: `independently-supported` for the separation and trace;
   local artifact/Return ownership remains pack authority, not professional
   evidence.

### Blind alternatives and rejected lanes

- **BCP 14 normative capitals:** useful where a document explicitly adopts
  them; rejected as a universal local vocabulary because RFC 8174 conditions
  their special meaning.
- **Full requirements or quality-model template:** useful as a review prompt;
  rejected as a mandatory filled form because NASA/NIST tailoring and
  applicability guidance supply direct counterpressure.
- **User stories alone:** useful for actor/goal/outcome framing; rejected as
  sufficient for a durable parent spec because they do not own interface,
  lifecycle, risk, or publication-recovery completeness.
- **Architecture document embedded in the spec:** rejected when it would decide
  new architecture; an owner pointer or already-settled constraint is the
  supported alternative.
- **Automatic create retry:** rejected unless the configured transport supplies
  an idempotency guarantee or the original mutation is proven unapplied.
- **Security/privacy/operability boilerplate:** rejected; derive obligations
  from applicable risk, data processing, users, and operating conditions.

## Conflicts, gaps, and rejected lanes

- **Story exhaustiveness versus commitment exhaustiveness:** independent sources
  support actors, goals, outcomes, traceability, and complete applicable

  should keep these as separate hypotheses.

  cost/brittleness and the value of lower-level tests.

  the exact M0 branch taxonomy and matrix form lack an accessible governing
