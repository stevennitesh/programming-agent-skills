### Independent findings

1. **Checklist-guided exhaustive coverage is independently supported under a
   bounded target.** NASA requires a checklist or formal reading technique and
   established completion criteria; Google instructs reviewers to understand
   every assigned human-written line while allowing scrutiny to vary by risk.
   GitHub's UI-specific "viewed" tracking was considered only an implementation
   example, not a necessary method. Claim label: `corroborated`. Method:
   `independently-supported`. M0-R04/R05/R13 should retain an explicit changed
   path/line inventory, documented skips, context expansion where needed, and
   a no-omission completion gate.

2. **Standards conformance and intended-function conformance are distinct,
   simultaneously required lenses.** NASA separately names requirements,
   design, required standards, latent errors, and traceability; Google separately
   examines functionality/user impact and documented style/design principles.
   Claim label: `corroborated`. Method: `independently-supported`. This supports
   M0's Standards/Spec split, but not a claim that the labels themselves are
   standard terminology.

3. **Finding admission should privilege evidence over preference and expose the
   requested consequence.** Google states that technical facts and data
   overrule opinion, undocumented pure-style preferences should not block, the
   reviewer should explain why, and severity/intent labels should distinguish
   required from optional feedback. The Microsoft study associates useful
   comments with concrete change-triggering feedback but also reports material
   construct and external-validity limits. Claim label: `corroborated` for
   evidence/reason/mandatory-status separation; `synthesis` for the local
   supported-scenario/evidence/impact/proof schema. Method:
   `independently-supported` for the former; the exact local Finding Contract
   remains intent-owned.

4. **Reviewer diagnosis and author repair are separable authorities.** Google's
   guide places repair responsibility with the author while allowing the
   reviewer to give proportionate guidance. Claim label: `direct`. Method:
   `independently-supported`. This supports M0-R10/R14's no-mutation boundary
   and remediation classification without requiring the reviewer to implement
   a fix.

5. **Readiness and completion criteria resist premature certainty.** NASA
   requires both and describes completion criteria as measurable finished
   activities that permit confidence in the outcome. Claim label: `direct`.
   Method: `independently-supported`, adapted from formal inspection. For this
   ordinary review, readiness means resolvable target, available required
   sources, and inspectable scope; completion means coverage, both judgments,
   finding admission, proof accounting, and snapshot read-back. The adaptation
   is an `inference`; NASA does not define the local fields.

6. **The immutable mixed snapshot needs separate identities for separate Git
   state locations.** Official Git manuals distinguish commit/tree, index,
   working tree, and untracked state. `git write-tree` can identify a fully
   merged index; diffs can identify staged and unstaged change content relative
   to pinned endpoints; status discovers untracked paths; and content hashes
   plus a deterministic path inventory can identify untracked content. Claim
   label: `synthesis` across B8-B12. Method: `independently-supported` as Git
   semantics, with the exact combined fingerprint a local design choice.
   Counterpressure: status alone misses untracked content changes, and
   `git diff` alone omits untracked files.

7. **Baseline discovery needs an ambiguity gate.** Git documents that multiple
   best merge bases can exist and that, without `--all`, the selected one is
   unspecified. Claim label: `direct`. Method: `independently-supported`.
   Therefore a since-X default should name the resolved ref and require exactly
   one applicable best common ancestor (or return incomplete); silent selection
   is not trustworthy.

8. **Major-first navigation is useful only with a full-coverage tail.** Google
   recommends understanding the change, reviewing major design areas first, and
   then traversing the remaining files without misses. The Microsoft study found
   lower useful-comment density as file count increased and advised smaller
   incremental changes, while explicitly limiting generalization to large,
   mature Microsoft projects using one review environment. Claim label:
   `corroborated` for major-first plus exhaustive tail; `direct` but bounded for
   the size association. Method: `independently-supported`. Counterpressure:
   fixed order by filename is simple and auditable, while major-first depends on
   sound identification of the central change. H1 should test any ordering
   mechanic rather than assume effectiveness.

9. **Security and safety review create legitimate counterpressure against a
   universal ordinary checklist.** NASA focuses extra review on critical and
   complex code, and its formal inspection requirements include participants
   and action tracking beyond one read-only report. Claim label: `direct`.
   Consequence: keep ordinary review bounded and route high-risk work; do not
   import a heavyweight inspection ceremony into M0 or H1.

### Reconciled verification

- The upstream and local **separate-axis** idea has independent support as a
  requirements-versus-standards distinction. The stronger mechanic of
  independent or serially reset perspectives is **contested**: T2 supports PBR
  in industrial code inspection, while T3 failed to reproduce its effectiveness
  and identified low process conformance. Neither directly evaluates a single
  LLM agent. The current Standards-to-Spec lens reset is therefore a reasonable
  protected local mechanic, but any claim that stronger isolation or parallel
  reviewers improves this skill must remain an H1 experiment.

- T1 corroborates a **coverage ledger** as an operational technique: progress
  is tracked per file and stale file review state is invalidated when content
  changes. It does not establish that GitHub's UI or file-only granularity is
  necessary. An H1 ledger should cover paths, hunks/lines, contextual reads,
  proof, and skips without importing PR state.

- Upstream severity schemes agree on distinguishing blocking defects from
  optional feedback, but their labels conflict. Google uses mandatory versus
  Nit/Optional/FYI, Superpowers uses Critical/Important/Minor, GitHub has
  Comment/Approve/Request changes, and current local review uses P0-P3 plus an
  independent remediation class. Shared usage supports **explicit consequence**,
  not any universal severity vocabulary. The exact local taxonomy remains
  intent-owned and should not be replaced from upstream repetition.

- Ponytail's tag-plus-replacement pattern is useful only inside its
  complexity-only Charter. Its net-line estimate is `pack-specific` and
  unverified as a measurement. Importing it into ordinary review would collapse
  axes and admit false precision; reject it for H1.

- Superpowers' file-backed diff package is a `pack-specific` transfer mechanism.
  Its underlying stable-snapshot principle is independently supported by Git,
  but a mandatory copied package would add machinery when the current skill can
  capture and identify an immutable snapshot directly. Retain only the identity
  principle unless evaluation exposes context-transfer failure.

### Alternatives and rejected lanes

- Deterministic path order is cheaper and more auditable than major-first
  traversal; it remains the control.
- A status-only snapshot is cheaper but cannot identify untracked content; a
  diff-only snapshot also omits it.
- One blended verdict is shorter but can hide which authority failed; reject.
- Formal multi-person inspection, tracked repair closure, and required expert
  participants exceed this skill's read-only ordinary-review Charter; route
  higher-risk work instead.
- Security-specific review frameworks are relevant to routed high-risk review,
  not a universal H1 checklist for this ordinary skill.
