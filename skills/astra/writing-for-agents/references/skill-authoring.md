# Skill authoring

Use for changes to discovery, invocation, packaging, or model/host adaptation.
Use the available host's `skill-creator` guidance and current documentation for
schemas and packaging mechanics when needed; this reference adds the pack's
authoring boundaries. Do not create a second packaging standard.

## Discovery and ownership

Keep the description to the smallest reliable task selector and nearest useful
exclusion. Test the intended boundary against realistic requests when it changes;
put procedure and rationale in the body or relevant reference.

Preserve invocation policy and unrelated metadata. Keep folder, frontmatter, and
invocation names consistent. Verify host behavior when material: listed metadata
does not establish that a skill loaded, and invocation settings do not necessarily
hide its description.

Edit the source package under its installation owner's rules. A source edit does
not install the change or authorize changes to other repositories or hosts.

## Receiver and evidence

Design for the actual receiver. On a model upgrade, consider subtracting obsolete
scaffolding before adding more. Keep any still-needed model or host adaptations
conditional so they do not constrain other receivers. Preserve project meaning
and real authority boundaries regardless of model capability.

Use the package's validator and check affected links and resources. For a
consequential method or discovery change, use
[Behavior evaluation](behavior-evaluation.md) to decide what behavioral evidence
would support the claim. A valid package alone establishes neither useful
behavior nor reliable selection.
