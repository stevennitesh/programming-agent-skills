# Reconcile existing guidance

Use this reference for an explicit pack migration, compatibility update, or repair
of known stale agent guidance. Do not use it merely because local wording differs
from current templates.

## Identify what actually needs migration

Trace the active root and nested instructions, referenced guides, and mechanical
enforcement affected by the changed pack behavior. Focus on guidance that can
change future agent decisions:

- retired or renamed skill routes;
- obsolete mandatory workflows such as unconditional ticketing, TDD, or delegation;
- stale setup fields or installer commands;
- duplicated or conflicting current owners; and
- inherited boilerplate that now imposes behavior the current pack no longer owns.

Preserve verified repository facts, accepted domain meaning, deliberate local
policy, and useful explanatory history. A rule is not a deliberate local choice
merely because an older bootstrap copied it into a repository-owned file, but do
not erase an override without evidence about its ownership.

Use local decisions, comments, history, and actual consumers when provenance
matters. If provenance remains consequentially ambiguous, ask its owner rather
than silently keeping an obsolete default or replacing a real project policy.

## Reconcile behavior, not templates

Current seeds are examples of the pack's present defaults, not target mirrors.
Compare a seed only when the affected local guidance claims the same ownership
or inherits the changed behavior. Equivalent local wording can remain unchanged.

Replace obsolete inherited mechanisms in place. When a workflow has no current
replacement, describe direct work or remove the retired route instead of inventing
another mandatory step. Do not append new guidance beneath a conflicting old rule
and call the migration complete.

When deliberate local policy differs from a current pack default, preserve it
unless the user asked to reconsider that policy. Surface only differences whose
consequences matter to the requested migration.

## Apply the authorized migration

If the user requested the migration, apply settled changes within that scope
without adding another approval cycle. Ask only for unresolved consequential
policy choices.

Update affected guidance and any narrow mechanical enforcement that specifically
encodes the displaced convention. Preserve the underlying protection when it
still matters. Do not bypass a failing check merely because it enforces an older
mechanism; determine whether the check itself is stale or whether it reveals a
still-valid contract.

Historical research and decision records remain evidence unless the user requested
their maintenance. Do not rewrite history to resemble current instructions.

## Verify the migration

Read the resulting path as a future agent. Confirm that:

- active instructions no longer select retired skills or obsolete workflows;
- current pointers resolve to accessible owners;
- preserved local policy remains clear;
- duplicate or conflicting obligations were removed; and
- affected mechanical checks now enforce the intended current contract.

A passing legacy validator establishes only its own legacy rules. It does not
prove current compatibility.

A repeat migration with no material behavioral difference should produce no edit.
Report the migrated surfaces, preserved local exceptions, and any unresolved
access or policy gap.
