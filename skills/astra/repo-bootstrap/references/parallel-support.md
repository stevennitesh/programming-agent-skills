# Parallel support

Read only for requested parallel setup or a concrete execution prerequisite gap.
The execution skill owns lane lifecycle, worker assignments, and live admission.
Bootstrap records repository environment choices and verifies capabilities; it
does not create worktrees, run a campaign, or infer permission changes from gaps.

Inspect the selected method and actual host configuration. For Astra
parallel-implement, establish Python and Git availability, the helper location,
a permitted lane root outside the repository, and whether worker commands can
use that root and isolated runtime paths. Preserve existing location and permission
preferences. Do not prescribe an obsolete host-specific schema or broaden access
without authority. Distinguish configuration found in source from effective
permissions and capabilities actually verified.

Record placement and runtime constraints at an existing repository-owned location,
or in a conditional parallel-execution guide linked from AGENTS.md. Name unresolved
prerequisites and evidence needed. Directory existence alone does not prove worker
access. Bootstrap inspection does not replace per-lane helper probes or worker
pre-mutation checks.

Check how the tracker represents active ownership, including a run identity when
several agents share an account. For local Markdown, preserve one canonical tracker
checkout and root-only writes during delivery. Record the selected location;
parallel-implement owns commit ordering and proof. Local tracker files are durable
even when their directory is named .scratch.

Include affected guide, tracker, pointer, and configuration edits in the existing
compatibility proposal. Apply already-authorized changes together and migrate
obsolete fields to the current Astra contract. If isolation is unavailable, report serial
execution as the fallback rather than claiming parallel readiness. Prose is not
a substitute for actual write permissions.
